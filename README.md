## Overview & Scope

When videos are deleted or an SD card is accidentally quick-formatted in a camera, drone, or PC, the video payload often remains completely intact in unallocated flash blocks until overwritten by new recordings.

`sd-video-recovery` is engineered specifically to extract these lost video files from SD cards safely and reliably on Windows:

- **Target Operating System**: Windows 10 and Windows 11 (64-bit `x86_64`).
- **Media Support**: SDSC, SDHC, SDXC, and SDUC cards up to 2 TB connected via native SD/MMC card readers or USB card adapters.
- **Filesystems**: FAT32 and exFAT (MBR, GPT, or unpartitioned superfloppy volumes).
- **Video Containers**: MP4 and MOV files generated by consumer, prosumer, and action cameras (GoPro, DJI drones, Sony, Canon, Panasonic, Nikon, Blackmagic, iPhone/Android).
- **Two Recovery Phases**:
  1. **Filesystem Metadata Recovery**: Recovers deleted directory entries (`0xE5` markers in FAT32, directory entry sets and `AllocationBitmap` InUse flags in exFAT). Where cluster chains remain intact, even physically fragmented files are fully restored. If the cluster chain was zeroed during deletion, safe contiguous extent fallback is applied.
  2. **Deep Sequential Raw Carving**: Performs an optimized, single-pass sequential scan across the disk for ISO-BMFF container boxes (`ftyp`, `mdat`, `moov`, `moof`). Reconstructs contiguous classic MP4/MOV and fragmented MP4 structures directly from raw sectors.
- **Deduplication Engine**: Automatically correlates raw carve candidates with filesystem metadata, ensuring filesystem candidates with preserved directory names and cluster maps take precedence without duplicate file dumps.
- **Bilingual Interface**: Native support for English (`en`) and Armenian (`hy`), automatically matching your Windows display language.

## Non-Goals & v1 Boundaries

To preserve strict safety and maintain predictable behavior, the following are explicitly out of scope for version 1:

- ❌ **No Raw NAND Flash / Chip-Off Recovery**: Cannot communicate with desoldered raw NAND flash memory or reverse-engineer manufacturer-specific wear-leveling algorithms.
- ❌ **No Physically Dead Controller Recovery**: Cannot recover cards that fail to register in Windows Disk Management or trigger fatal hardware I/O errors at LBA 0 (e.g. electrical failures, bad silicon controller).
- ❌ **No In-Place Filesystem Repair**: Will never execute `chkdsk`, modify partition tables, or write repair structures to the source SD card.
- ❌ **No Automatic Corrupt Bitstream Repair**: Does not heuristically re-encode or patch severed H.264/H.265 video frames beyond placing recovered bytes into valid ISO-BMFF containers.
- ❌ **No Heuristic Defragmentation for Lost Chains**: Does not guess random cluster orders for physically fragmented files whose cluster allocation metadata was wiped out during format.
- ❌ **Zero Telemetry / Zero Network Access**: Runs 100% offline with zero outbound network calls, telemetry, or analytics. Your private recordings never leave your machine.
- ❌ **Rust Library Stability**: In v1, the internal Rust library API does not carry a public stability guarantee. The official stable interfaces are the CLI executable and the versioned JSON report (`report_version: 1`).

## Safety Guarantees

Data recovery on fragile or failing flash media requires extreme discipline. `sd-video-recovery` enforces the following safety invariants by design:

1. **Strictly Read-Only Source Handle**:
   The physical disk (`\\.\PhysicalDriveN`) is opened with Win32 `CreateFileW` using only `GENERIC_READ`, `FILE_SHARE_READ | FILE_SHARE_WRITE`, and `OPEN_EXISTING`. No write handles or mutating IOCTLs are ever requested.
2. **System Disk Protection**:
   The tool automatically identifies the Windows boot/system drive (where `C:\Windows` lives) and categorically refuses to open or scan it.
3. **Storage Bus Verification**:
   The bus type is verified via `IOCTL_STORAGE_QUERY_PROPERTY`. Removable SD, MMC, and USB readers are permitted. Fixed internal drives (NVMe, SATA, RAID) are blocked by default to prevent user error, requiring both `--allow-fixed` and manual disk number confirmation.
4. **Mandatory Disk Number Confirmation**:
   Before initiating a scan in interactive mode, the CLI displays the device model, size, bus type, and detected partition table, requiring the user to type the physical disk number to proceed.
5. **Anti-Collision Destination Verification**:
   The destination directory must reside on a **different physical disk** than the source SD card. The software queries the physical disk extents of the output volume and immediately halts if they match the source drive, preventing overwriting the very media being recovered.
6. **Atomic File Extraction (`.part`)**:
   Recovered candidates are written to temporary `.part` files (e.g., `cand-0001_GOPR1234.MP4.part`). Only upon successful completion and validation are they atomically renamed to their final filenames.
7. **Overwrite Prevention (`create_new`)**:
   Files and session folders are opened with atomic `create_new` semantics. Existing files are never overwritten or truncated.
8. **Single-Retry Bounded Read on Media Errors**:
   If a bad sector or I/O failure occurs, the engine performs exactly **1 sector-level retry**. If the sector still cannot be read, it logs the exact byte offset to `report.json` and cleanly halts or isolates the candidate, preventing endless head thrashing or thermal degradation of failing flash cells.
9. **Graceful Cancellation (`Ctrl+C`)**:
   When interrupted via `Ctrl+C` (SIGINT), the active temporary `.part` file is deleted immediately. Already completed files are preserved intact, and an interrupted `report.json` is generated before exiting with code `130`.

## Prerequisites & External Tools

`sd-video-recovery` relies on the industry-standard FFmpeg suite for stream verification:

| Tool | Status | Purpose |
| :--- | :---: | :--- |
| **`ffprobe`** | **Mandatory** | Performs fast structural and metadata validation on recovered video files, verifying container headers and video stream parameters without reading every frame. |
| **`ffmpeg`** | **Optional** | Required only when `--full-verify` is specified. Decodes the entire video stream frame-by-frame to guarantee that no corruption or truncated frames exist. |

> [!IMPORTANT]
> **FFmpeg binaries are NOT bundled** in `sd-video-recovery` release archives. You must install FFmpeg on your Windows system or provide explicit paths.

### Installing FFmpeg on Windows

#### Option A: Windows Package Manager (`winget`) — Recommended
Run the following in PowerShell or Command Prompt:
```powershell
winget install Gyan.FFmpeg
```
Restart your terminal after installation to refresh your system `PATH`.

#### Option B: Chocolatey
```powershell
choco install ffmpeg
```

#### Option C: Manual Download
1. Download a release build from [gyan.dev/ffmpeg/builds](https://www.gyan.dev/ffmpeg/builds/) (e.g. `ffmpeg-release-essentials.zip`).
2. Extract the archive (e.g. to `C:\ffmpeg`).
3. Add `C:\ffmpeg\bin` to your Windows System `PATH` environment variable, or pass paths directly to `sd-video-recovery` via `--ffprobe-path` and `--ffmpeg-path`.

To verify your installation, run:
```powershell
sd-video-recovery doctor
```

## Installation & Quick Start

1. Download the latest release `.zip` (`sd-video-recovery-v0.1.0-x86_64-pc-windows-msvc.zip`) from GitHub Releases.
2. Extract the archive to any folder on your computer (e.g., `C:\Tools\sd-video-recovery`).
3. Open PowerShell or Command Prompt as **Administrator** (required to read raw physical drives like `\\.\PhysicalDriveN`).
4. Run `sd-video-recovery list` to find your SD card's physical disk number:
   ```powershell
   sd-video-recovery.exe list
   ```
5. Run the recovery command pointing to an output folder on your local drive (e.g., `D:\Recovered`):
   ```powershell
   sd-video-recovery.exe recover --disk 2 --output D:\Recovered
   ```

## CLI Reference

### `sd-video-recovery list`

Scans and enumerates all physical storage devices attached to the system, displaying device path, model, capacity, bus type, and partition schemes.

```text
USAGE:
    sd-video-recovery list [OPTIONS]

OPTIONS:
    --lang <en|hy>    Set interface language (default: Windows system locale)
    --json            Output the disk list in machine-readable JSON format
    -h, --help        Print help information
```

#### Examples:
```powershell
# Standard human-readable table
sd-video-recovery list

# Machine-readable JSON output for scripting
sd-video-recovery list --json

# Force Armenian language output
sd-video-recovery list --lang hy
```

### `sd-video-recovery recover`

Performs deep video recovery from the specified physical disk into a new timestamped session directory.

```text
USAGE:
    sd-video-recovery recover --disk <N> --output <DIRECTORY> [OPTIONS]

REQUIRED ARGUMENTS:
    --disk <N>               Physical disk number N (corresponding to \\.\PhysicalDriveN)
    --output <DIRECTORY>     Destination directory (must be on a DIFFERENT physical disk)

OPTIONS:
    --mode <MODE>            Scan mode:
                               all        Filesystem metadata first, then deep raw carve (default)
                               filesystem Filesystem metadata recovery only (FAT32/exFAT)
                               deep       Deep raw ISO-BMFF carving only
    --ffprobe-path <FILE>    Explicit path to ffprobe executable
    --ffmpeg-path <FILE>     Explicit path to ffmpeg executable
    --full-verify            Perform full video frame decode via ffmpeg (slow, exhaustive)
    --allow-fixed            Permit scanning fixed internal drives (requires confirmation)
    --lang <en|hy>           Set interface language (default: Windows system locale)
    -h, --help               Print help information
```

#### Examples:
```powershell
# Standard full recovery from PhysicalDrive2 to D:\Recovered
sd-video-recovery recover --disk 2 --output D:\Recovered

# Fast metadata-only recovery (e.g. recovering recently deleted files where directory entries remain)
sd-video-recovery recover --disk 2 --output D:\Recovered --mode filesystem

# Exhaustive raw carving with full frame-by-frame video stream decoding
sd-video-recovery recover --disk 2 --output D:\Recovered --mode deep --full-verify

# Armenian interface
sd-video-recovery recover --disk 2 --output D:\Recovered --lang hy
```

### Process Exit Codes

`sd-video-recovery` adheres to standardized process exit codes for easy scripting and automation:

| Code | Name | Description |
| :---: | :--- | :--- |
| **`0`** | `Success` | Scan completed successfully, or `list`/`doctor` command succeeded. |
| **`2`** | `InvalidArgs` | Invalid command line arguments, unrecognized options, or missing required parameters. |
| **`3`** | `SafetyPreflight` | Safety violation: destination is on the same physical drive, target is a system disk, target is a fixed drive without `--allow-fixed`, interactive confirmation was rejected, or output collision occurred. |
| **`4`** | `SourceIo` | Persistent read error encountered on the source disk after 1 sector retry. |
| **`5`** | `ExternalTool` | External dependency (`ffprobe` or `ffmpeg`) is missing, inaccessible, or failed during validation. |
| **`130`** | `Interrupted` | Execution was interrupted by the user pressing `Ctrl+C` (SIGINT). |

## Session Output Layout

Every recovery run creates an isolated, timestamped session directory inside your destination folder. Existing folders or files are never overwritten:

```text
<output-directory>/
└── session_20261108_143022/
    ├── validated/
    │   ├── cand-0001_GOPR0042.MP4
    │   ├── cand-0002_DJI_0105.MOV
    │   └── cand-0004_raw_00800000.MP4
    ├── partial/
    │   └── cand-0003_raw_00450000.MP4
    ├── report.json
    └── summary.txt
```

- **`validated/`**: Contains files that passed `ffprobe` container and video stream validation (and full frame decode if `--full-verify` was enabled). These files are ready for editing or playback.
- **`partial/`**: Contains files that contain recognizable video container boxes or partial streams, but failed full validation (e.g., truncated tail, corrupted index). Kept for manual inspection or specialized video repair tools.
- **`report.json`**: Machine-readable, versioned recovery audit report detailing all candidates, physical offsets, extents, hashes, and validation logs.
- **`summary.txt`**: Localized (English or Armenian) human-readable summary of the session results.


### Candidate Status Values:
- **`validated`**: The file was extracted and verified by `ffprobe` as having valid container headers and at least one decodable video stream. Moved to `validated/`.
- **`partial`**: Video metadata was found, but the file was truncated or exhibited stream syntax errors during verification. Moved to `partial/`.
- **`rejected`**: False positive candidate or severely corrupt data that failed to yield a decodable stream. Not dumped to disk.
- **`io_error`**: Extraction was aborted because of persistent hardware read errors on the source SD card at the recorded offset.

### Candidate Confidence Levels:
- **`high`**: Directory entry intact, cluster chain or exFAT `NoFatChain` intact, and verified by `ffprobe`.
- **`medium`**: Directory entry found but cluster chain zeroed (contiguous extent assumed), or raw carving candidate with clean box boundaries.
- **`low`**: Truncated box structure, orphan `mdat` fragment, or structural anomalies detected.

## Manual Sacrificial SD Card QA Checklist

To thoroughly test recovery without risking production footage, maintain a dedicated **sacrificial SD card** (e.g. 16 GB or 32 GB) and follow this verification protocol:

```text
[ ] STEP 1: Preparation & Baseline
    1. Insert the dedicated sacrificial SD card into your USB/SD card reader.
    2. Format the card as exFAT or FAT32.
    3. Copy 3-5 known test MP4 and MOV videos (e.g., recorded on GoPro or drone).
    4. Compute and record the baseline SHA-256 hash of each file:
       Get-FileHash E:\*.MP4, E:\*.MOV -Algorithm SHA256

[ ] STEP 2: Deletion Scenario QA
    1. Delete one or more video files through Windows Explorer (Shift+Delete).
    2. Run: sd-video-recovery.exe list (verify physical disk number, e.g. 2).
    3. Run: sd-video-recovery.exe recover --disk 2 --output D:\RecoveryTest --mode filesystem
    4. Confirm that deleted files are extracted into 'validated/'.
    5. Verify recovered files match baseline SHA-256 hashes exactly.

[ ] STEP 3: Quick-Format Scenario QA
    1. WARNING: Double-check that your sacrificial test card is selected!
    2. In Windows Disk Management or Explorer, perform a QUICK FORMAT on the test card.
    3. Run: sd-video-recovery.exe recover --disk 2 --output D:\RecoveryTest --mode deep --full-verify
    4. Confirm that candidates are carved from unallocated space.
    5. Verify that 'validated/' contains playable MP4/MOV videos and that ffmpeg full-verify succeeded.

[ ] STEP 4: Safety Invariant Verification
    1. Confirm the source card was never written to (timestamp and volume serial match).
    2. Attempt to run recovery pointing output to the test card itself:
       sd-video-recovery.exe recover --disk 2 --output E:\RecoveryTest
       -> Verify it immediately fails with Exit Code 3 (Safety Preflight Failure).
    3. During a deep scan, press Ctrl+C:
       -> Verify the engine immediately deletes any incomplete .part file and cleanly exits with Exit Code 130.
```
